NCC MES PoC — Acceptance Test Plan

One test per Action Tracker item · 11 August 2026 · run these before submitting to the client

How to read this Every test names the exact screen, the exact filter, and the exact number to look for. Where a screen could lie convincingly, there is a database query that reads the raw truth — check the screen against the query, not against your expectation.
The one rule that decides every disagreement GET /production/oee/calculate is the reference. If a screen disagrees with it for the same scope and window, the screen is wrong — not the reference. Several tests below use this.

ID 2Big Betti signals → automatic event detectionVerified live — 14 Aug 2026

Tests the whole chain: Modbus signal → machine state → downtime event with a timestamp.

  1. Confirm the status tags exist and are being read: 
    SELECT t.code, t."signalRole", t."registerType", t.address, v.value, v.timestamp
FROM tag_current_values v JOIN tag_definitions t ON t.id = v."tagId"
WHERE t."isMachineStatus" ORDER BY t.address;
    Five rows, all registerType = DISCRETE with a signal role, timestamps within the last minute: M1_RUN_MODE DI 2, M3_RUN_MODE DI 3, M4_RUN_MODE DI 4 (pulsed), M5_TABLE_ROTATION DI 4 on the second module, M5_RUN_MODE DI 5. These are NCC's I/O IDs 3, 4, 5, 5 and 6 — the ID is one-based and the DI is zero-based, so DI = ID − 1.
  2. Stop Big Betti: 
    echo '{"stopped":["M1"]}' > apps/edgegateway/sim-control.json
  3. Wait 30 seconds, then check the state and the event: 
    SELECT m.code, s.state FROM machine_current_status s
JOIN machines m ON m.id = s."machineId" WHERE m.code = 'M1';

SELECT m.code, d."reasonCode", d.category, d."startTime", d."endTime" IS NULL AS open
FROM downtime_events d JOIN machines m ON m.id = d."machineId"
WHERE d."startTime" >= now() - interval '5 minutes' ORDER BY d."startTime" DESC;
  4. Open localhost:8080/downtime and confirm the event is listed
  5. Restart it: echo '{"stopped":[]}' > apps/edgegateway/sim-control.json — the event must CLOSE (endTime set)
Expected: M1 goes to a stopped state; one open downtime event appears with a real start timestamp; it closes when the machine restarts.
Observed 14 Aug 2026: M1 BREAKDOWN, event UNPLANNED_BREAKDOWN / MECHANICAL opened 14:00:46 and closed 14:04:26 — 3.67 min, no manual step.

On the physical panel the same tag bindings apply unchanged; what must be confirmed on site is the wiring and the sense of each contact (whether ON means running for that particular module). Both are per-tag settings on IoT → Signal Rules, so a correction at commissioning needs no code change.

ID 10Starved detected automaticallyVerified live — 14 Aug 2026
Why this cannot be done from Run Mode alone. NCC's own signal document says Cartomac and Uni-Tech report Run Mode ON "including the condition where the machine is ready, but no product is currently being processed". A starved machine on this line never looks stopped, so waiting for a stop to classify would never fire at all. The second signal NCC supplied — Uni-Tech's table rotation, which "indicates that a pallet is being processed" — is what separates working from waiting. Run Mode says the machine is able to work; the table says whether it is working.
  1. Confirm all machines are RUNNING
  2. Stop the filler: echo '{"stopped":["M1"]}' > apps/edgegateway/sim-control.json
  3. Wait for the buffers to drain (the simulator prints WIP pieces; watch filled reach 0), then for the table's idle threshold to elapse — configured per signal on IoT → Signal Rules, default 5 minutes
  4. Check the states: 
    SELECT m.code, s.state FROM machine_current_status s
JOIN machines m ON m.id = s."machineId" ORDER BY m."sortOrder";
  5. Check the classification: 
    SELECT m.code, d."reasonCode", d.category, d."isPlanned"
FROM downtime_events d JOIN machines m ON m.id = d."machineId"
WHERE d."endTime" IS NULL ORDER BY m."sortOrder";
Expected: M1 stays a plain stop (nothing feeds it — it cannot be starved). A machine that is ready but not processing becomes STARVED with reasonCode = STARVED and category = MATERIAL.
Observed 14 Aug 2026, 13:54:20 — M5 STARVED / MATERIAL / isPlanned=false, after the table's idle threshold was set to 30 s from the edge dashboard (no redeploy).
Also confirm the guards. Three of them, and each one exists because firing too eagerly is worse than not firing — an over-eager inference moves real losses out of the machine's OEE and flatters the equipment.
  • Stop only the middle machine (M3) while its neighbours run: it must stay a breakdown, not become starved.
  • A machine with no table-rotation signal must stay RUNNING, never guessed into STARVED.
  • A downstream machine that is itself STARVED must not make the machine before it read as BLOCKED. That cascade would invert the line — the true starvation at the head reported as a blockage behind it — and hide the real constraint. This was caught by live verification on 14 Aug, not by the unit tests, and is now pinned by four tests.
Notes:
ID 11Blocked detected automaticallyVerified live — 14 Aug 2026
  1. Reset: echo '{"stopped":[]}' > apps/edgegateway/sim-control.json, wait for all RUNNING
  2. Stop the last machine: echo '{"stopped":["M5"]}' > …
  3. Wait for the accumulation to back up, then re-run the two queries from test 10
Expected: M5 stays a plain stop (nothing follows it — it cannot be blocked). The machine feeding it becomes BLOCKED with reasonCode = BLOCKED and category = PROCESS.
The mirror-image guard. An upstream machine that is itself BLOCKED must not make the machine after it read as STARVED. A blocked machine has product it cannot pass on — usually because this machine stopped taking it. Reading that as starvation blames the upstream for a jam this machine caused, and books the loss as external so it is removed from OEE — the machine would be rewarded for its own blockage.
Notes:
ID 12Starved/Blocked excluded from OEE lossIPIC Closed

The most important test in this document. It proves a machine waiting on the line is not punished for waiting.

  1. With machines in STARVED from test 10, note their Availability on /production/oee
  2. Confirm the starved minutes are booked as an external loss, not an availability loss: 
    SELECT m.code, sum(s."downMin") down_min
FROM production_snapshots s JOIN machines m ON m.id = s."machineId"
WHERE s."bucketStart" >= now() - interval '30 minutes' GROUP BY m.code;
  3. On the hierarchy tree, check externalLossMin is non-zero for the starved machines
Expected: Availability for a starved machine stays high. The starved time appears as external loss, not as an availability loss.
Worked example: 480 min planned, 120 starved, 360 run → A = 100%, not 75%.

9b · Configuration — nothing that matters is compiled in

A PoC that only works because the values were baked in is not a product. These tests check that the decisions a plant owns — what a contact means, what a stop costs, and what raises an alarm — are all editable, from the application and from the edge gateway's own dashboard.
C-1Signal interpretation is configurableMust pass
  1. Open IoT → Signal Rules. The Bound signals table should list the five NCC status signals with their roles and thresholds.
  2. Open IoT → Tag Browser, edit M5_TABLE_ROTATION, and change Idle before Starved from 300000 to 30000 ms. Save.
  3. Stop the filler and confirm M5 reaches STARVED in about 30 s instead of 5 min — with no restart and no redeploy.
  4. Repeat the change from the edge gateway dashboard (http://localhost:4900 → Tag Browser) and confirm it takes effect the same way.
Expected: the threshold, the signal role, and the pulse window/edges are all editable in both places, and the gateway picks the change up within its cache window without being restarted.
Notes:
C-0Only an administrator can change what a signal costsMust pass

The Signal Rules page decides what a stop costs in OEE. Hiding a link is not access control — check that the door is locked, not merely unlabelled.

  1. Sign in as a Viewer or an Energy Manager. Confirm Signal Rules does not appear under IoT in the sidebar.
  2. Type the URL directly: localhost:8080/iot/signal-rules. You must get a clear "you do not have access" page naming the missing permission — not the editor, and not a page that loads and then fills with errors.
  3. Confirm the same user can still open IoT → Tag Browser. The lock is on configuration, not on monitoring.
  4. Sign in as a Factory Admin and confirm the page opens and saves.
  5. From Access Control, grant iot:signals to whichever engineer role should hold it on this site, and confirm that user gains the page with no redeploy.
Expected: the page and every state-rule and alarm-definition endpoint return 403 for a user without iot:signals, and 200 for one with it.
Verified 14 Aug 2026: Viewer and Energy Manager got 403 on all four endpoints while keeping 200 on /iot/tags; Factory Admin got 200/201 throughout.
Why a separate permission from iot:manage. Managing a gateway is operational work. Turning "charged against OEE" off for changeover rewrites every availability figure in the plant, retroactively and silently. iot:read is held by six roles including Viewer, so inheriting from it would have left that switch open to almost everybody.

9c · Planned stops — nothing is deducted that nobody entered

What changed, and why it matters to every OEE number on this system Each shift template carried breakMinutes and cleaningMinutes, both defaulting to 30. Those 60 minutes were subtracted from planned production time, so they set the availability denominator for the whole plant — and on this installation neither had ever been changed from the default. The generator also decided when they happened (break at the shift midpoint, cleaning at the end) and applied both to every active machine, recording downtime against equipment nobody had touched.

Planned stops are now rows with a name, a duration, a start time and a scope. The denominator is derived from them, so every deducted minute traces to something a person created.
P-1The denominator is explicableMust pass
  1. Open Planning → Planned Stops. The four stops migrated from the old settings are listed, each flagged as having no target.
  2. Check a shift template: GET /api/v1/shifts/templates. Confirm plannedProductionMinutes equals the shift duration minus the stops listed in plannedStops — and that you can arrive at the number by hand.
  3. Delete one stop and re-read. The denominator must move by exactly that stop's duration.
Expected: 12 h shift with two 30-minute stops → 660 planned minutes. Verified 14 Aug 2026 on both SDPF shifts. Remove one stop and it becomes 690 — no hidden term.
Notes:

  3. Query the events and check which days appear.

X-3Performance is not pinned at 100%Currently fails on NCC data
SELECT m.code,
       round((sum(s."idealRunMin") / NULLIF(sum(s."runMin"),0) * 100)::numeric, 1) AS perf_uncapped
FROM production_snapshots s JOIN machines m ON m.id = s."machineId"
WHERE s."bucketStart" >= now() - interval '30 minutes'
GROUP BY m.code ORDER BY m.code;
Expected: every machine below 100, and the machines differing from one another.
This is the query that exposes the cycle-time problem. The screens clamp Performance at 100%, so a value of 162% or 248% is invisible there — it shows as a perfect 100%. A KPI pinned to its ceiling carries no information, and "every machine at 100% Performance" is the least believable thing a demo can show. The simulator now runs at the bottleneck pace so this reads realistically; the underlying master-data disagreement is NCC's to correct.
