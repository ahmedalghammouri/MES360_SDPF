## 2. الأسباب الجذرية — مُثبتة، لا مُفترضة

### السبب #1 — محرّكان للـ OEE يقرآن من مصدرين مختلفين

في `kpi.service.ts:649`:

```ts
if (this.snapshotsEnabled() && !opts.workOrderId && !opts.productionOrderId) {
  return this.snapshotAggregate(...);   // ← مخزن الحقائق
}
const jos = await this.prisma.jobOrder.findMany({ ... });  // ← مسح حيّ
```

`SNAPSHOTS_READ=on` في بيئة التشغيل (تحقّقت منها داخل الحاوية). إذن:

* **المحرّك أ — مخزن الحقائق** (`production_snapshots`، 31,585 صفاً، آخر تحديث 2026-08-08 03:29):
  يخدم `/oee/calculate` و`/oee/trend` و`/dashboard/*`.
* **المحرّك ب — مسح Job Orders الحيّ**:
  يخدم `/oee/hierarchy` (جزئياً) و`/oee/line` و`/oee-records` و`/production/kpis`.

المحرّكان **لم يُختبر تطابقهما أبداً**، ولا يوجد اختبار واحد يثبّت أنهما يعطيان نفس الرقم لنفس المدخلات.

### السبب #2 — شرط النافذة الزمنية في المحرّك ب **خاطئ** (هذا سبب الصفر)

الشرط المستخدم في أربعة مواضع (`kpi.service.ts:660, 902, 1024, 1107, 1197`):

```ts
OR: [ { actualStart: { gte: from, lte: to } },
      { actualEnd:   { gte: from, lte: to } } ]
```

هذا يعني: «اعرض أوامر التشغيل التي **بدأت** داخل النافذة أو **انتهت** داخلها».
والصحيح هو: «اعرض ما **يتقاطع** مع النافذة».

الحالة الفعلية في قاعدة البيانات الآن:

```
Big Betti        | 1 JO | actualStart 2026-08-07 07:31 | actualEnd NULL
Cartomac         | 1 JO | actualStart 2026-08-07 07:31 | actualEnd NULL
Checkweigher     | 1 JO | actualStart 2026-08-07 07:31 | actualEnd NULL
Euro-Pack Robot  | 1 JO | actualStart 2026-08-07 07:31 | actualEnd NULL
Uni-tech Wrapping| 1 JO | actualStart 2026-08-07 07:31 | actualEnd NULL
```

أمر التشغيل بدأ **أمس** ولم ينتهِ بعد. مع نافذة 2026-08-08:
* `actualStart` خارج النافذة ✗
* `actualEnd` = NULL ✗

النتيجة: **صفر صفوف ← OEE = 0**.

هذا يفسّر بالضبط وبشكل قاطع:
* `Overall Line OEE = 0.0 %` مع `A 0.0 / P 0.0 / Q 0.0`
* `Machine OEE Leaderboard: No OEE records found for this period`
* كل ماكينة في استجابة `/oee/line` تعود بصفر

**التصحيح المطلوب:**
```ts
AND: [
  { actualStart: { lte: to } },
  { OR: [ { actualEnd: null }, { actualEnd: { gte: from } } ] },
]
```
(حساب المدة نفسه مُقصوص على النافذة بالفعل عبر `overlapMin` — الخلل في الاختيار فقط، لا في الحساب.)

### السبب #3 — تعريفان مختلفان لكلمة «Shift»

* `getOEESummary` عندما `timeframe='shift'` يتجاهل `dateFrom/dateTo` ويحسب النافذة من **قوالب الورديات** → `بداية الوردية → الآن` (نافذة متحرّكة، تتغيّر كل ثانية).
* `/oee/line` و`/oee/hierarchy` و`kpi/*` تستخدم `resolveRange(dateFrom, dateTo)` → **يوم تقويمي كامل بتوقيت UTC**.
* والواجهة (`useTimeRange`) تبني التواريخ بالتقويم **المحلّي** (UTC+3)، بينما `resolveRange` يلحق `Z` ويجبرها على UTC.

فرق ثلاث ساعات مُدمج في نفس الشاشة.

### السبب #4 — لماذا «Unassigned» في Insights Studio

التجميع حسب الوردية في `snapshotGrouped` يستخدم:
```sql
COALESCE("shiftInstanceId", '__noshift')   → التسمية الاحتياطية 'Unassigned'
```

والواقع في قاعدة البيانات:

| الجدول | العدد |
|---|---|
| `production_snapshots` | 31,585 صفاً — **`shiftInstanceId` فارغ في كلها (0)** |
| `work_orders` | 3 أوامر — واحد فقط مرتبط بوردية |
| `shift_instances` | **سجل واحد فقط في النظام كله**، بتاريخ 2026-07-27 |

الكاتب ينسخ `jo.workOrder.shiftInstanceId` (`production-snapshot.service.ts:198`) — وهو فارغ دائماً.

**السبب الحقيقي: النظام لا يُنشئ `ShiftInstance` تلقائياً.** الـ Command Center يعرض «Shift 2 — Night» لأنه يستنتج الوردية الحالية من **القوالب** لا من السجلات. أي أن للنظام مفهومين للوردية: واحد محسوب لحظياً وآخر مُخزَّن — والمخزَّن فارغ عملياً.

### السبب #5 — مصدر ثالث للعدّ في كارت الوردية (7851 %)

`Output Progress · CARTON  274,800 / 3,500` — وهذا لا يأتي من أي من المحرّكين السابقين، بل من **عدّادات التليمتري الخام** (`shift.service.ts:504`):

```ts
cur.good += meta.goodDelta ?? 0;   // من أحداث COUNT_UPDATE
```

فبينما يقول محرّك OEE إن إنتاج الوردية ≈ 195,000 قطعة، يقول هذا المسار 274,800 كرتونة (≈ 1.1 مليون قطعة). فارق **5.6×**. والهدف 3,500 قيمة افتراضية في قالب الوردية لم تُضبط على الواقع أصلاً.

### السبب #6 — حدّ nginx يُسقط طلبات عشوائياً (سبب اللاتكرارية)

من `infrastructure/nginx/nginx.conf:57`:
```
limit_req_zone $binary_remote_addr zone=api:10m rate=300r/m;   # 5 طلبات/ثانية
limit_req zone=api burst=50 nodelay;
```

وفي `providers.tsx`: `refetchOnMount: 'always'` + `refetchOnWindowFocus: true`.

صفحة داش بورد واحدة تُطلق عشرات الاستعلامات دفعةً واحدة (كروت + شارات القائمة الجانبية)، فتتجاوز الـ burst فوراً. سجلّ الـ console الذي أرسلته يُظهر **مئات** الطلبات المتطابقة لـ `/production/oee/hierarchy` ترجع 429، ومعها تسقط `work-orders` و`ncr` و`capa` و`alarms` و`inspections`.

**كل استعلام يرجع 429 → React Query يعيد `undefined` → الكارت يرسم `0`.**
وهذا هو سبب أن الأرقام تختلف **حتى بين تحديثين لنفس الصفحة**: كل مرة تسقط مجموعة مختلفة من الطلبات.

> ملاحظة: التكرار المئات من المرات لنفس الرابط يتجاوز ما تفسّره سياسة إعادة المحاولة (محاولتان). يوجد على الأرجح حلقة إعادة تركيب في الواجهة تحتاج تأكيداً داخل المتصفّح — لم أستطع إثباتها بلا متصفّح، وأُدرجها كبند مفتوح لا كحقيقة.

### السبب #7 — أخطاء عرض

* **عنوان Factory Analytics مكتوب «Energy Analytics»** — خطأ في ملف الترجمة `en/modules.json:1430` (`analytics.title`). الصفحة سليمة، الاسم خاطئ فقط.
* **`178,870.511 units`** — كسور عشرية ظاهرة للمستخدم ناتجة عن تحويل الوحدات في مخزن الحقائق (`goodBase`/`totalBase` أرقام عائمة). العدد يجب أن يُقرّب قبل العرض.
* **React error #418** — عدم تطابق بين ما يرسمه الخادم وما يرسمه المتصفّح (hydration mismatch)، يُجبر React على إعادة رسم الشجرة كاملة.
* **الخط أقل من المنطقة التي يحتويها** (PL-01 = 24.9 % تحت Packing = 60.4 %) — ليس خطأ حسابياً: عقدة الخط تُحسب بطريقة **BOTTLENECK** بينما المنطقة تُحسب بـ **ROLLUP**. لكن عرضهما في شجرة واحدة بلا بيان للطريقة يجعله يبدو خطأ. هذا هو بالضبط ما طلبتَه سابقاً: **تعميم بيان الطريقة على كل الصفحات.**

## 3. الإجابات المباشرة على أسئلتك الثلاثة

**1. لماذا «Unassigned» في Insights Studio؟**
لأن `shiftInstanceId` فارغ في **كل** الـ 31,585 صفاً في مخزن الحقائق، ولأن النظام كله يحتوي على **سجل وردية واحد** عمره 12 يوماً. الورديات لا تُنشأ تلقائياً؛ الـ Command Center يعرض اسم الوردية لأنه يستنتجها من القوالب لا من السجلات.

**2. لماذا Overall Line OEE = 0؟**
لأن شرط اختيار أوامر التشغيل في `/oee/line` يطلب أن تكون قد **بدأت أو انتهت** داخل اليوم، وأمر التشغيل الجاري بدأ **أمس ولم ينتهِ** — فلا يطابق أياً من الشرطين. صفر صفوف ← صفر OEE. نفس السبب أفرغ «Machine OEE Leaderboard».

**3. لماذا صفحة Factory Analytics اسمها Energy Analytics؟**
مفتاح ترجمة خاطئ في `apps/web/src/locales/en/modules.json:1430`.

# القسم الثاني — أمر الإنتاج / أمر التشغيل / الوحدات

**العيّنة:** `PO-8-8-2026` → `WO-2026-0001` (طلب حيّ أُنشئ اليوم)
**المنتج:** Alwatani Powder Detergent — Blue 4×4 Kg C · `unitsPerInner=1، innersPerCarton=4، cartonsPerPallet=40`
→ **1 كرتونة = 4 قطع · 1 باليت = 40 كرتونة = 160 قطعة**

## 6.1 الخطة سليمة تماماً — لا خطأ فيها

من `job_orders` مباشرةً:

| # | العملية | المخطط داخل | المخطط خارج |
|---|---|---|---|
| 1 | Filling | 40,000 PIECE | 40,000 INNER |
| 2 | Weighing | 40,000 INNER | 40,000 INNER |
| 3 | Cartoning | 40,000 INNER | **10,000 CARTON** |
| 4 | Palletizing | 10,000 CARTON | **250 PALLET** |
| 5 | Wrapping | 250 PALLET | 250 PALLET |

40,000 قطعة = 10,000 كرتونة = 250 باليت. **سلّم الوحدات في التخطيط صحيح ومتّسق مئة بالمئة.**

## 6.2 العدّ الفعلي هو المكسور — والسبب واحد

من نفس الجدول، الأعمدة الفعلية:

| # | العملية | `actualQtyGood` | `outputUnit` | = بالقطع |
|---|---|---|---|---|
| 1 | Filling | 420 | INNER | 420 |
| 2 | Weighing | 0 | INNER | 0 |
| 3 | Cartoning | 416 | CARTON | **1,664** |
| 4 | Palletizing | 0 | PALLET | 0 |
| 5 | Wrapping | **424** | PALLET | **67,840** |

الخمس ماكينات تعدّ **نفس التدفّق الفيزيائي** بنفس المعدّل تقريباً (420 / 416 / 424)، لأن العدّاد في [counter.service.ts:237](apps/edgegateway/src/acquisition/counter.service.ts#L237) يزيد **واحداً لكل نبضة حسّاس**:

```ts
await this.prisma.jobOrder.update({ data: { actualQtyGood: { increment: inc } } });
```

ثم يُفسَّر هذا العدّاد بوحدة الخطوة. النتيجة:

> **نفس 420 وحدة فيزيائية تُقرأ 420 قطعة عند الحشو، و1,664 قطعة عند الكرتنة، و67,840 قطعة عند التغليف. تضخّم ×160 على آخر خطوة.**

في الواقع لا تنبض ماكينة التغليف إلا **مرّة كل 160 قطعة**. المحاكي/التغذية تُنبض كل الماكينات بنفس المعدّل بغضّ النظر عن سلّم التعبئة.

وبما أن `kpi.service.ts:169` يأخذ **الخطوة الأخيرة** كإنتاج أمر التشغيل:
```ts
const totalCount = (last.actualQtyGood ?? 0) + (last.actualQtyRejected ?? 0);
```
فإن كل رقم إنتاج في النظام مبنيّ على العدّاد الأكثر تضخّماً.

## 6.3 عيب ثانٍ مستقل: وحدة أمر التشغيل مكتوبة خطأً في قاعدة البيانات

```
production_orders : targetQty 10000 | unit CARTON     ← الصحيح
work_orders       : plannedQty 10000 | qtyUnit PIECE  ← خطأ
```

الرقم نُسخ من أمر الإنتاج **بدون وحدته**، فأخذ القيمة الافتراضية `PIECE` من الـ schema. المفروض 10,000 كرتونة = **40,000 قطعة**. أي أن **المقام أصغر 4×** بينما البسط أكبر 160×.
