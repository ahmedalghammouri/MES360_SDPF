Executive Narrative

1. Executive Summary — What Changed in the Final PoC

The original PoC concept assumed broader PLC/SCADA data availability. During execution, direct PLC access became impractical due to client-side constraints and the requirement to avoid any operational risk. The final PoC therefore uses a controlled IoT overlay architecture — unchanged from the previous revision.

Final Implementation Direction MES360 receives validated production events from external carton sensors through Remote I/O, IoT gateways and a packaged on-prem Edge Node Gateway. Machine status, stoppages and downtime reasons are captured by line operators through a tablet interface.
The important correction: MES360 is a full MES, not a PoC dashboard The platform delivered for this engagement contains 29 backend modules and over 100 operational screens covering production, quality, maintenance, inventory, traceability, energy, IoT/historian, scheduling, alarms, analytics and administration. The PoC does not build a limited subset — it activates a subset of an existing platform. Everything not activated on the Betti line is a configuration and master-data exercise, not new development.
Why this is the right PoC approach
Zero PLC Risk No PLC program changes, no direct machine control, no production interruption.
Fast Visibility Counts and downtime classification become visible immediately using existing line-side signals and the tablet workflow.
Proven Scale Path The same dashboards already consume Modbus TCP/RTU, OPC UA and MQTT sources — so adding approved PLC tags later is configuration, not a rebuild.
Final PoC focus
What the PoC Measures Automatically
  • Good carton count (rising-edge counter at the gateway)
  • Rejected carton count
  • Production rate and line output
  • Event timestamping, buffering and traceability
  • Gateway and device health telemetry
What Operators Manage on Tablet
  • Machine operational state
  • Stop start/end and downtime reason codes
  • Shift and product/job-order context
  • Scrap logging and remarks
  • Supervisor validation of exceptions

Constraint Landscape

2. Current State Constraints & Final Design Decision

The final design intentionally separates production visibility from PLC dependency. This protects the PoC schedule, avoids changes to legacy controls, and keeps the evaluation focused on measurable operational value.

PLC Data Constraint Client-side PLC tags, communication ports and approved access were not sufficiently available for a direct PLC-based PoC.
Operational Constraint The PoC must not modify PLC logic, interrupt machine cycles, or introduce risk to production continuity.
Business Decision Use non-intrusive sensors for counting and tablet-driven workflows for machine state and downtime classification.
Resulting architecture principle
Sense Capture physical carton events externally using carton sensors wired to Remote I/O.
Normalize Debounce, filter duplicates, timestamp and buffer at the Edge Node Gateway.
Operate Use tablets to manage status, stops, reasons, scrap and remarks.
MES360 Value Convert simple edge events and operator context into a live plant model: real OEE, downtime Pareto and root-cause analysis, quality yield and non-conformance tracking, asset reliability, material traceability, and an exportable KPI report pack — all from one calculation engine so every screen reconciles.
Constraint is on the data source, not on the platform It is important that the evaluation team reads the PLC constraint correctly: it limits which signals are available today. It does not limit what MES360 can compute or display. The platform's acquisition layer already supports Modbus TCP, Modbus RTU (serial and RTU-over-TCP), OPC UA and MQTT, with a time-series historian behind it. The moment approved tags exist, they flow into the same dashboards without redevelopment.

Line-Side Execution

5. Operator Tablet Workflow for Machine Status & Downtime

Because machine states and downtime reasons are not available from PLC tags during the PoC, the tablet becomes the controlled operational interface for capturing context in real time. The screens below are delivered product, not PoC mock-ups.

1. Select Shift / Product / Job Order Operator opens the current shift and the job order to run; the line, machine and product context is bound automatically from the plant hierarchy.
▼
2. Set Machine Status Running, stopped, idle, cleaning, changeover, maintenance or waiting material — every transition is written to the machine state history that feeds availability.
▼
3. Classify Stop Reason When a stop occurs the operator selects a reason code from the configured ISA-95 reason set, adds remarks, and the stop is timed live until it is closed.
▼
4. Log Scrap / Rejects Reject quantities are logged against the job order with a reason, feeding scrap rate, defect Pareto and, where required, a non-conformance record.
▼
5. Validate & Report Supervisor reviews open stops and exceptions, acknowledges events, and exports the shift / daily KPI report pack.

Decision Thresholds

7. PoC KPI Framework & Calculation Logic

The KPI model uses the available data sources: sensor counters for quantities, tablet events for operating time and stoppages. All formulas below are the ones implemented in the product — every screen reads one calculation engine, so figures reconcile.

KPIFormula as implemented
Good / Reject CountSensor-validated accepted and rejected cartons, normalised to the product base unit
Quality %Good ÷ (Good + Reject) × 100
First Pass YieldΣ inspection pass qty ÷ Σ inspection total qty × 100 — units accepted at first inspection, before rework
Defect Rate / PPMΣ inspection fail qty ÷ Σ inspection total qty × 100 (and × 1,000,000 for PPM). FPY + Defect Rate = 100
AvailabilityRun time ÷ planned production time, from machine state and downtime events. A time-based (AT-OEE) variant is reported alongside
PerformanceActual rate ÷ ideal rate, from the configured ideal cycle time per SKU
OEEAvailability × Performance × Quality, time-weighted across job orders — not a simple average of daily values
Downtime by ReasonStop minutes grouped by reason code, ranked with cumulative % (Pareto), split planned vs unplanned
MTBF (equipment)(Capacity hours − all downtime hours) ÷ breakdown stop count
MTTR (equipment)Σ breakdown stop hours ÷ breakdown stop count
MTBF / MTTR (maintenance)Operating hours ÷ corrective+emergency work orders raised; Σ repair hours ÷ repairs completed
KPI integrity — how the numbers are kept honest
One Engine, Not Per-Screen Maths Reliability, OEE and quality KPIs are each computed by a single shared service, so the command centre, the module cockpit and the analytics report cannot disagree.
Definitions Travel With Numbers Each KPI screen carries an on-page methodology panel: formula, data source, and the inclusion / exclusion rules applied.
Reconciliation Built In Where two valid measurement bases exist (e.g. reliability from machine stops vs from work orders), both are shown side by side with the variance explained.
Honest caveats that remain for this PoC
  • Performance requires the ideal cycle time per SKU to be confirmed by NCC. It is a configuration input, captured during the alignment workshop; until it is set, performance is reported against the agreed nameplate rate.
  • Machine state is operator-declared, not PLC-derived. Availability accuracy therefore depends on tablet discipline — which is why it is an explicit success criterion.
  • Reliability KPIs are meaningful once a maintenance history exists on the line; with a short evaluation window they should be read as a trend, not an absolute.

Success Criteria

9. PoC Success Criteria & Acceptance Measures

The PoC should be judged against measurable operational outcomes that fit the final non-intrusive architecture. The criteria below define a clear basis for evaluation and the scale-up decision.

Sensor Count Accuracy Good and rejected carton counts align with physical shift records after calibration.
Data Collection Stability Remote I/O, IoT gateways and the Edge Node Gateway remain stable during live evaluation, with buffered recovery after any network loss.
Dashboard Usability Management can view output, reject count, status and downtime without manual consolidation.
Tablet Compliance Operators classify stops and maintain machine status updates during production.
Downtime Visibility Top downtime reasons and durations are visible at shift and day level.
KPI Integrity The same KPI reads identically across the command centre, module cockpit and analytics report for the same period — verified during UAT.
Recommended numeric thresholds
Accuracy TargetCounter variance ≤ 2–3% vs manual count after calibration.
Logging Target≥ 90% of stops over 3 minutes carry a reason code.
Availability TargetData acquisition uptime ≥ 95% during evaluation.
Reconciliation TargetZero unexplained KPI variance between screens for the same window.
Recovery Target100% of buffered edge events recovered after a network interruption.
Reporting TargetShift and daily report pack produced without manual data handling.
Acceptance Output Signed PoC KPI report, live dashboard demonstration, KPI methodology sheet, issue log, and a scale-up recommendation.

Scale-Up Path

11. Roadmap Beyond the PoC

The roadmap is deliberately reframed in this revision. The phases below are activation and integration milestones, not development milestones — the functionality already exists in the delivered platform.

Phase 1 — Stabilise the PoC Sensor count calibration, operator tablet discipline, dashboard adoption and the daily KPI pack on the Betti line.
Phase 2 — Activate Adjacent Modules Switch on quality (inspections, NCR, SPC), maintenance (work orders, PM, spares) and inventory for the same line. Configuration and master data only.
Phase 3 — Enrich Machine Signals Add stack-light, alarm-relay or other non-invasive signals to automate machine state and reduce reliance on manual status entry.
Phase 4 — Direct PLC / SCADA Integration Map approved PLC tags over Modbus or OPC UA, validate security, and cut over from operator-declared to machine-derived states.
Phase 5 — Line and Site Rollout Replicate the proven line template across remaining packaging lines and areas using the same hierarchy, reason codes and KPI definitions.
Phase 6 — Enterprise Layer ERP / Oracle integration, energy monitoring from installed meters, advanced scheduling, and predictive maintenance models.
Recommended scale-up decision Proceed with MES360 production rollout keeping the sensor/tablet architecture as the baseline, activating adjacent modules first — because they deliver value without field work — and adding approved PLC/SCADA tags progressively where the business value justifies the integration effort.
