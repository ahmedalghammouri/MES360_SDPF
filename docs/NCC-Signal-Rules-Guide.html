Signal Rules — Configuration Guide

NCC · SDPF · how a contact becomes a state, what that state costs, and where to change it

The whole page in one sentence Bound signals decide what a wire means; State rules decide what that meaning costs in downtime and OEE. They are two different questions, which is why they are two different tables.

1 · The chain, end to end

Everything between the first box and the last is configuration held in the database. The gateway re-reads it within 30 seconds, so no change here needs a restart or a redeploy.

2 · Bound signals — what a wire means

One row per physical point that carries machine state. Configure it from IoT → Signal Rules → Bind a signal, or on the tag itself in the Tag Browser.

The five roles

RoleWhat it assertsThresholds it uses
RUN_MODE ON = the machine is running or ready with nothing to process. It does not, on its own, separate working from waiting. none
RUN_MODE_PULSED Judged by rhythm, not level: steady ON = running, pulsing = stopped, OFF = alarm. Euro-Pack Robot signals this way. pulse window · minimum edges
PROCESSING Product is actually being worked. This is the signal that separates a machine that is producing from one that is merely able to. idle before starved
INFEED_AVAILABLE Material is arriving. OFF while stopped is read as Starved. none
OUTFEED_BLOCKED Cannot discharge. ON while stopped is read as Blocked. none
Why PROCESSING exists at all NCC's own signal document says Cartomac and Uni-Tech report Run Mode ON "including the condition where the machine is ready, but no product is currently being processed". On this line a starved machine never looks stopped. Any rule that waits for a stop before classifying it would never fire. Run Mode says the machine is able to work; the wrapping table's rotation says whether it is. Without a PROCESSING signal bound, starvation on that machine is undetectable — not wrongly detected, simply invisible.

The thresholds, and how to choose them

FieldMeaningHow to pick it
Pulse window (ms)
default 6000		 How far back the gateway looks when deciding whether the bit is oscillating. A few pulse periods, so one missed poll does not read as steady.
Minimum edges
default 4		 How many transitions inside that window count as "pulsing". Raise it if electrical noise is being read as a stop.
Idle before Starved (ms)
default 300000 = 5 min		 How long a PROCESSING signal may stay inactive before the machine counts as waiting rather than mid-cycle. The machine's slowest normal cycle. The wrapping table rests minutes between pallets; a filler does not.
The idle threshold is the one to get right Too short and the system reports starvation between every pallet — inventing external losses, removing them from the machine's OEE, and flattering equipment that was working fine. Too long and a real stoppage goes unrecorded. Over-reporting is the worse failure of the two, so the default errs long. Set it to 30 s only for a demonstration, never for a running plant.

Effect on the system

  • Decides which machine state is written, which is what opens and closes downtime events.
  • A status tag with no role is read literally through its status map and takes no part in starvation or blockage detection. The page marks these in amber — it is a silent half-configuration, not a blank.
  • Counting is not affected. A pulse that arrives is a unit that was made; it is counted regardless of what the state signal says. Signals change the time analysis, never the quantity.

3 · State rules — what a state costs

One row per state, per factory — with an optional override per machine. This is where a plant states its own policy.

FieldWhat it decidesWhere you see the effect
Open a downtime event Whether entering this state creates a downtime record at all, closed when the machine leaves it. Downtime Command Center · MTTR / MTBF · downtime Pareto
Planned stop Marks the event as planned. Planned minutes are not counted as unplanned downtime. Availability · planned-vs-unplanned split in reports
Charged against OEE Off means the minutes are recorded but excluded from the availability loss. Availability, and therefore OEE
Reason code · Category How the stop is classified before anybody touches it. Downtime analysis, Pareto grouping, exports
Debounce (s) How long the state must hold continuously before it is believed. Event count integrity — see below

Precedence

rule for THIS machine  →  factory-wide rule  →  gateway built-in default

So one awkward machine can be treated differently without forking the whole table, and deleting a rule falls back rather than losing the record. If the configuration cannot be read at all, the built-in default still applies: a stop is never lost because a lookup failed.

What ships, and why

StateDowntimePlannedCharged to OEEDebounceReasoning
RUNNINGno——0 sProducing.

SETUP / CHANGEOVERyesyesyes0 sPlanned, but still a loss by default — this is the one plants most often disagree on.

BLOCKEDyesnono5 sExternal, exactly as STARVED.
OFFLINEyesnono0 sNo signal. Recorded, not charged as a fault.
Why STARVED and BLOCKED carry a longer settling time They are derived from the states of neighbouring machines, so they move whenever a neighbour moves. Live running on 14 Aug 2026 recorded three BLOCKED events for one machine inside two seconds, 0.6 s each. The total minutes were roughly right, but the event count was nonsense and the log was unreadable. Debounce fixes the count without touching the minutes.

4 · Worked example — turning off a policy you disagree with

Suppose NCC decides changeover should not be charged against the machine.

  1. IoT → Signal Rules → State rules, edit CHANGEOVER.
  2. Turn Charged against OEE off. Save.
  3. Within 30 seconds the gateway is applying the new rule.

From that moment changeover minutes are still recorded and still visible in the Downtime Command Center, but they no longer reduce Availability. Nothing was rebuilt, and no engineer was involved.

This applies going forward, not backwards The flag is stamped onto each downtime event as it is created. Events already closed keep the value they were created with. That is deliberate — a KPI that silently changes for a month you already reported on is worse than one that changes from today.

5 · Two exclusions, not one — read this before tuning OEE

A state can be kept out of the OEE loss by two different mechanisms, and they are not the same switch:

MechanismKeyed onConfigurable?
Charged against OEE on the state rule The flag stored on each downtime event Yes — per factory and per machine, from this page
External loss subtracted from planned production time before Availability and Performance are derived The state name being STARVED or BLOCKED No — that list is still fixed in the KPI engine
The honest limitation Setting STARVED to "charged against OEE" would make its downtime event count against availability, but the second mechanism would still subtract those minutes from planned production time, because that subtraction is keyed on the state name and not on the rule. In other words: which states count as "external" is not yet configurable, only what each state costs as a downtime event. For NCC's PoC the shipped defaults are consistent and this never bites. It is recorded here so nobody discovers it by getting a surprising number.

7 · Checking your work

-- what the machines are doing right now
SELECT m.code, s.state
FROM machine_current_status s JOIN machines m ON m.id = s."machineId"
ORDER BY m."sortOrder";

-- what it was classified as, and whether it counts
SELECT m.code, d."reasonCode", d.category, d."isPlanned", d."affectsOEE",
       d."startTime", d."endTime", d."durationMinutes"
FROM downtime_events d JOIN machines m ON m.id = d."machineId"
WHERE d."startTime" >= now() - interval '30 minutes'
ORDER BY d."startTime" DESC;

If an event is shorter than the state's debounce, the settling time is not being applied. If a machine sits in a state you did not expect, check its bound signals first — the state is only ever as good as what the wire was said to mean.
